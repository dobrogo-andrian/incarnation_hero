# 2 Архітектура

## 2.1 Межа ядро / представлення

```
[Godot UI] --Command--> [Core: Simulation] --SimEvents + оновлений стан--> [Godot UI]
                                │
                        [PlayerView: знання гравця]
```

- **Command** — намір гравця: StartMeditation(direction, weeks), Travel(zoneId), CombatMove(hex), ChooseEventOption(id) тощо. Ядро валідує команду і або виконує її, або відхиляє з причиною.
- **SimEvent** — типізований запис того, що сталося: WeekPassed, InjuryReceived, RumorAppeared, BreakthroughResult… UI використовує їх для анімацій і журналу, симулятор — для метрик.
- **Стан** — серіалізовані дані без логіки. Логіка живе в системах.
- **Ядро не знає про реальний час, кадри й Godot.** Немає DateTime.Now, немає статичного глобального стану, немає непрямого рандому.

## 2.2 Режими гри

Скінченний автомат у ядрі:

Overworld (керування часом) → EventDialog (вибір у події) → Combat (покроковий бій) → RunEnd.

Кожен режим приймає лише свої команди. Перехід між режимами — це теж SimEvent.

## 2.3 Модель часу

- **Тік = 1 тиждень.** Вік зберігається як ціле число тижнів. Кількість тижнів у році — параметр балансу weeks_per_year, за замовчуванням 52 (D16).
- **Активність** — дія з тривалістю в тижнях: медитація, тренування, подорож, лікування. Гравець задає тривалість або «до кінця».
- **Покроковий цикл тижня:**
   1. глобальні системи світу: старіння, згасання бафів, відновлення й виснаження ці в місцях, загоєння травм, прогрес суперників, вікна чуток;
   1. прогрес активності гравця: приріст фундаменту, шкали, статів;
   1. кидок подій для поточного контексту;
   1. збір **переривань**.
- **Переривання** — категоризовані сигнали: нова чутка, подія, баф вичерпано, ці місця на мінімумі, шкала етапу заповнена, травма загоїлась, наближення кінця життя. Категорії, що зупиняють прискорення, налаштовує гравець; набір зберігається в стані забігу, і ядро повідомляє й про незупиняючі переривання (D22). Переривання із зупинної категорії і подія з вибором завершують активність: гравець вирішує наново (D45). Усамітнення прориву переривання не зупиняють. Події з вибором зупиняють час завжди.
- **Прискорення — суто UI-поняття.** Ядро просто виконує тижні, доки не з'явиться переривання або не скінчиться активність. UI вирішує, анімувати кожен тиждень чи прокрутити миттєво. Тому «медитація до смерті» — це звичайна активність без обмеження тривалості.

## 2.4 Стан

```
GameState
 ├─ RunMeta: seed, версія контенту, номер забігу
 ├─ Clock: поточний тиждень
 ├─ Player: Character + PlayerKnowledge
 ├─ World: Region (зони, переходи, місця медитації зі станом ці), Settlement, Sects, Shops
 ├─ Npcs: суперники (спрощена модель)
 ├─ Rumors: активні чутки (істинний зміст + заявлений зміст)
 ├─ ActiveActivity / ActiveCombat / ActiveEvent
 └─ RngState: стани всіх потоків
```

MetaProfile (окремий файл): резонанс душі за категоріями, статистика, налаштування

**Character** (див. дизайн §2):

- базові стати: Міць, Витривалість, Швидкість, Сила меридіан. [Робоче припущення: канонічний список з §2.1];
- Сприйняття;
- ресурси: здоров'я, стеля здоров'я, енергія тіла, пул ці;
- культиваційні треки (2.6), фундамент (знання, чистота), токсини, активний метод, активні бафи;
- передумови: корінь душі, тип тіла, схильності до стихій;
- вивчені техніки (рівень, майстерність), рівні стихій;
- травми, інвентар, вік, тривалість життя.

## 2.5 Система модифікаторів

Єдиний механізм для травм, бафів, стихій, методу, предметів, профілів аспектів:

```
Modifier { StatId, Op (Add | Mul | Override | Cap), Value, SourceId, Duration?, StackRule }
```

Ефективні стати обчислюються з бази й активних модифікаторів, з кешем, який скидається при зміні. У коді ціль модифікатора — `TargetId`: стат, аспект або максимум ресурсу; значення утворюють ланцюжок стат → аспект → максимум ресурсу, і кожна ланка застосовує свої модифікатори за тим самим правилом (D28). `StackRule` поки одне: те саме джерело на ту саму ціль замінює попередній модифікатор. Кешу поки немає — обчислення дешеве; додамо, якщо профілювання покаже потребу. UI показує розкладку «звідки це число» безпосередньо з джерел модифікаторів. Це закриває вимогу читабельності без окремого коду.

## 2.6 Культиваційні треки

```
CultivationTrack { VectorId, StageIndex, StageProgress, LastBreakthroughQuality }
```

Етапи описані в даних для кожного вектора: content/cultivation/qi_stages.yaml. У MVP існує лише вектор qi. Вектори body і will — це нові файли даних плюс точкові розширення систем. Окремих систем для них **не будуємо** зараз, лише не забороняємо їх появу.

## 2.7 Істина і знання

- Ядро тримає **істинний стан** усього.
- PlayerView — проєкція, через яку UI бачить світ: стани інших персонажів, надійність чуток, приховані зони, прогноз прориву.
- Функція спостереження Observe(viewer, target, aspect) → Observed<T> повертає значення або діапазон залежно від Сприйняття і різниці етапів. Вищий етап дає жорсткий бар'єр. Базова інформація (відносний етап, видимі серйозні травми) видима завжди.
- **Правило:** UI ніколи не читає істинний стан чужих сутностей напряму. API ядра для UI видає лише PlayerView. Це правило дешево дотримувати з першого дня і дуже дорого запроваджувати потім.

## 2.8 Детермінізм і RNG

- Власна реалізація PRNG (xoshiro256** або PCG) із сидуванням через SplitMix64. System.Random не використовуємо, щоб не залежати від реалізації рантайму.
- **Окремі потоки**, похідні від майстер-сиду: worldgen, events, rumors, npc, loot, combat, ai. Кожен бій отримує власний підсид із потоку combat. Так додавання кидка в одній системі не зсуває результати в інших.
- Стани всіх потоків зберігаються в сейві.
- **Правила детермінізму:**
   - жодної ітерації по Dictionary/HashSet, від якої залежить результат: використовувати впорядковані колекції або сортування за ID;
   - жодної паралельності в симуляції;
   - double дозволено, але проміжні результати, що йдуть у стан, округлюються за явними правилами.
- **Гарантія:** однаковий сид + однакова послідовність команд + однакова збірка = однаковий результат. Відтворюваність між версіями гри не гарантується. Для реплеїв балансу це прийнятно.
